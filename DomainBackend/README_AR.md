# x-sign.web.app — تثبيت XSign بدون Pairing

هذه الحزمة تُجهّز الجزء الخاص بالدومين. وجود الملفات في مستودع التطبيق لا يعني أن Firebase نشرها. لا تستخدم Firebase كخادم لتوقيع التطبيقات أو تخزين IPA أو P12. التوقيع ونقل IPA يظلان على جهاز المستخدم.

## ترتيب تشغيل التحديث

1. انشر حزمة الدومين في مشروع موقع Firebase الحالي بالطريقة أدناه، ثم شغّل verify.py.
2. استبدل `.github/workflows/XSign_Internal_Signing_Server.yml` في مستودع `ipablack/X-SIGN` بالملف المحدّث. لا يحتاج RESTORE_TOKEN أو PAT إضافياً.
3. من Actions شغّل **XSign Pairing-Free Local Installation**. يفحص Ubuntu خدمة الدومين واختباراتها أولاً؛ إذا نجح يبدأ macOS اختبارات Swift وHTTPS ثم يبني IPA.
4. لا تُحفظ تغييرات Swift في الفرع إلا بعد نجاح الاختبارات والبناء. نزّل **XSign-Pairing-Free-IPA** من التشغيل الناجح وثبّت الإصدار الجديد. تغيير GitHub لا يحدّث التطبيق المثبت تلقائياً.

إذا توقف preflight، راجع جاهزية الخدمة ولا تعاود أكشن Pairing القديم. حزمة الدومين متاحة أيضاً كمرفق **XSign-Domain-Backend** من مرحلة Ubuntu حتى إن فحص الدومين لم ينجح. لا ينشر ملف تحديث التطبيق أي شيء إلى Firebase.

## المسار

1. XSign يوقّع محلياً بالشهادة المستوردة، ثم يُجهز IPA مؤقتاً في التخزين الخاص.
   يقرأ معرّف الحزمة ورقم البناء CFBundleVersion من Info.plist داخل النسخة الموقعة؛ لا يستبدل رقم البناء برقم العرض المختصر المخزن في قائمة التطبيقات.
2. سيرفر HTTPS داخل التطبيق يستمع على 127.0.0.1 ومنفذ عشوائي، ويعطي iOS مساراً عشوائياً مؤقتاً. لا يستمع على الشبكة المحلية.
3. يرسل التطبيق معلومات التطبيق وعنوان ملف التثبيت المحلي إلى `POST https://x-sign.web.app/native/prepare` عبر HTTPS. لا تُرسل بايتات IPA أو كلمات مرور أو شهادات التوقيع.
4. يرجع الدومين رابط manifest يحمل تذكرة AES-GCM مشفرة؛ لا يظهر عنوان IPA في رابط التذكرة أو رسالة التطبيق. iOS يقرأ XML من الدومين ثم ينقل IPA من الجهاز نفسه.
5. لا يوجد زر تصدير أو نسخ/مشاركة الرابط، وتُحذف النسخة المؤقتة عند الإنهاء أو الإلغاء. إغلاق التطبيق قسرياً أو تعليق iOS له قد يوقف التثبيت.

**حد الاعتماد:** x-sign.web.app من Firebase، ولا يمثل عنوان سيرفر الآيفون. HTTPS المحلي يستخدم مادة TLS العامة من `backloop.dev` كما في Feather؛ تُحفظ نسخة خاصة مؤقتة، ويتحقق iOS من صلاحية الشهادة دون تجاوز الثقة. عند فشل الشهادة المخزنة يحاول التحديث مرة واحدة. هذه ليست استقلالية عن خدمة SSL/DNS الخاصة بـBackloop. محرك توقيع التطبيقات مستقل عنها.

## نشر الجزء الخاص بالدومين مرة واحدة

المشروع الذي تشير إليه وثائقك السابقة هو `xsign-bd088` والموقع `x-sign`. تحقق من تطابقهما في حساب Firebase قبل النشر. لم تتحقق هذه المراجعة من صلاحيات حسابك أو تنشر الموقع، ولم تُفعّل فوترة.

Cloud Functions وSecret Manager يحتاجان مشروعاً مهيّأً للخدمات اللازمة؛ نشر Functions يتطلب خطة Blaze وفق Firebase. لا تشغّل أمر النشر ما لم يكن حساب المشروع وصلاحياته وخطته مناسبين لك. حد maxInstances=2 وconcurrency=2 يقلل الموارد، لكنه ليس سقف تكلفة مضموناً ولا مصادقة ضد كل إساءة استخدام. الحد حسب IP داخل كل instance فقط.

من **مجلد موقع Firebase الحالي** الذي يحتوي `firebase.json` وملفات صفحاتك الأصلية:

```bash
python3 /path/to/X-SIGN/DomainBackend/configure.py .
npm install --prefix functions_xsign_ota
```

سكربت الدمج يرفض إنشاء Hosting فارغ، ولا يستبدل صفحات الموقع أو إعدادات المواقع الأخرى. يحتاج عنصر Hosting صريحاً يحتوي `site: "x-sign"` أو `target: "xsign"`، ويحتفظ بمجلد public/source الحالي. يضع مسارات native قبل قاعدة SPA العامة، ويضيف codebase منفصلاً اسمه xsign-ota.

بعد تسجيل دخول Firebase بحساب المشروع المالك، خزّن مفتاح AES عشوائياً كسر على الخادم؛ لا تضعه في Swift أو المستودع:

```bash
xsign_manifest_key_file="$(mktemp)"
openssl rand -hex 32 > "$xsign_manifest_key_file"
firebase functions:secrets:set XSIGN_OTA_MANIFEST_KEY --data-file "$xsign_manifest_key_file" --project xsign-bd088
rm "$xsign_manifest_key_file"
```

راجع `firebase.json` بعد الدمج. إذا استعملت target=xsign مرتبطاً بالموقع x-sign:

```bash
firebase deploy --project xsign-bd088 --only functions:xsign-ota,hosting:xsign
```

إذا استعملت `site` بدلاً من target فاستخدم محدد Hosting المعتمد لموقعك في المشروع الحالي. لا تنشر بقية المواقع دون داعٍ، ولا تستبدل مجلد الموقع بمجلد مستودع التطبيق.

## اختبار النشر

```bash
python3 /path/to/X-SIGN/DomainBackend/verify.py
```

النجاح يتطلب JSON صحيحاً من `/native/status` ونجاح prepare وXML صحيح من رابط التذكرة على x-sign.web.app نفسه. رجوع صفحة index.html أو redirect أو 404 لا يعني نجاح الخدمة. الاختبار يستخدم عنوان loopback تجريبياً ولا يُرسل IPA أو شهادة.

إعادة توليد المفتاح تُبطل التذاكر الجارية. انتظر انتهاء التثبيتات الحالية قبل تدويره. بعد النشر الصحيح يبقى اختبار تثبيت فعلي على iPhone بشهادة مناسبة ضرورياً؛ بناء IPA واختبار XML لا يثبتان قبول كل إصدار iOS.

## ما لا تضمنه هذه الحزمة

- لا يمكن منع استخراج الملفات على جهاز مكسور الحماية أو من نسخة معدلة. نظام iOS نفسه يحتاج بايتات الملف للتثبيت.
- تبقى روابط مصادر التطبيقات العامة متاحة من جهة المصدر؛ إخفاء أزرار النسخ لا يحوّلها إلى مصدر خاص.
- تذكرة manifest قابلة للقراءة المتكررة حتى انقضائها لأن iOS قد يعيد الطلب. عنوان IPA لا يخدم خارج loopback، وتُلغى صلاحيته عند إغلاق الجلسة أو انتهاء مهلتها.
- Backend لا يجلب روابط ولا يخزن ملفات أو بيانات جلسات. سجلات الاستضافة قد تحتفظ بالتذاكر المشفرة وعناوين IP؛ لا توجد سجلات تطبيقية لعنوان IPA أو محتوى POST.
- ليس هناك ضمان لتوقيع دون شهادة صالحة، أو لتثبيت IPA مشفّر بـFairPlay أو ذي استحقاقات غير مسموحة.
